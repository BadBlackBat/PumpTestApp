# PumpTestApp - внутренняя документация (логика и алгоритмы)

Этот файл - НЕ для конечных пользователей программы. Он описывает, как
устроена логика внутри кода: почему принимались те или иные решения,
как работают алгоритмы синхронизации, защиты и паролей. Предназначен
для того, кто будет дальше дорабатывать/поддерживать программу.

---

## 1. Архитектура многопользовательской работы

### 1.1. Общий принцип

Программа **всегда** читает и пишет только в свою **локальную** копию
базы данных (`database.get_active_db_path()` безусловно возвращает
`db_settings.get_local_db_path()`, даже когда включён сетевой режим).
Сетевой файл (`db_settings.get_network_db_path()`) - это просто общая
точка обмена, к которой программа обращается только в конкретные,
явные моменты:

1. При старте программы - сверка версий, копирование при необходимости
   (`db_sync.check_and_sync_at_startup`, вызывается из `main.py`)
2. Периодически во время работы (раз в 8 секунд, в фоновом потоке) -
   проверка изменений + присутствие пользователей
   (`gui.py: _RemoteCheckWorker`, `db_sync.check_for_remote_changes`)
3. По кнопке "Выгрузить" - копирование локальной базы в сеть
   (`db_sync.push_local_to_network`)
4. По кнопке "N -> L" - принудительное копирование сети в локальную базу
   (`db_sync.force_pull_network_to_local`)

Такая архитектура была выбрана вместо прямой работы с сетевым файлом
(SQLite по сети ненадёжен для одновременной записи с нескольких машин),
и вместо неё же естественно ложится офлайн-режим - "работаю локально,
пока не нажму кнопку" работает одинаково что при рабочей сети, что при
её полном отсутствии.

### 1.2. Ревизия базы данных (db_meta.revision)

Каждая операция записи (`database.bump_revision()`) увеличивает
ревизию. Формат: `ГГММДД * 1000 + счётчик_за_день` (год идёт ПЕРВЫМ,
не как в привычном ДД.ММ.ГГ отображении) - это критично для того, чтобы
обычное числовое сравнение "какая ревизия больше" совпадало с
хронологическим порядком. Если бы день шёл первым (как в отображении),
сравнение ломалось бы на стыке месяцев/годов (например, 01.01.27 как
число оказалось бы МЕНЬШЕ, чем 31.12.26).

Отображение для человека - `database.format_revision_display()`,
разбирает число обратно и показывает в привычном ДДММГГ.счётчик виде.

### 1.3. Точка синхронизации (db_settings.last_sync_revision)

Отдельное значение (не путать с ревизией самой базы!) - локальная
ревизия НА МОМЕНТ, когда локальная копия последний раз точно совпадала
с сетью (после pull или после успешного push). Статус
"синхронизировано"/"есть изменения" (`db_sync.is_synced()`) - это
просто сравнение текущей локальной ревизии с этой точкой.

Важный нюанс в `check_and_sync_at_startup()`: если локальная ревизия
БОЛЬШЕ сетевой (у пользователя есть локальные правки, которые ещё не
были в сети - например, накопленные до включения сетевого режима),
точка синхронизации НЕ обновляется - иначе статус ошибочно показал бы
"синхронизировано", хотя на самом деле есть неотправленные изменения.

### 1.4. Лок-файл (db_lock.py)

Эксклюзивный лок-файл (`<сетевой_путь>.lock`) - создаётся ТОЛЬКО на
момент самой записи в сетевой файл (доли секунды: скопировать
локальный файл поверх сетевого), не на всё время редактирования в
диалоге. Используется в `push_local_to_network()`,
`smart_merge_push()`.

**Критический урок из отладки**: нельзя полагаться на mtime сетевой
папки (метаданные файловой системы) для определения "протух ли лок" -
на реальной сетевой шаре mtime отставал от локальных часов клиента на
~223 секунды. Вместо этого время создания лока хранится ВНУТРИ его
содержимого (`хост:пользователь:время`), и проверка возраста лока
сравнивает это записанное время с ТЕКУЩИМ временем того же самого
процесса, который его читает - то есть всегда с самим собой, а не
полагается на чужие метаданные.

### 1.5. Присутствие пользователей (db_sync.py: update_presence,
get_active_user_count)

Каждый компьютер раз в 8 секунд обновляет свой файл-метку
(`<сетевая_папка>/active_users/<имя_пользователя>.presence`) с текущим
временем внутри. Другие компьютеры читают эти файлы и считают, сколько
из них "свежие".

**Критический урок из отладки**: НЕЛЬЗЯ сравнивать время, записанное
ОДНИМ компьютером, с текущим временем ДРУГОГО - часы разных машин в
сети не обязательно синхронизированы (на практике наблюдалось
расхождение, из-за которого один компьютер всегда видел чужие метки
как "протухшие"). Правильный подход - `_presence_seen_cache` (модуль-
уровневый словарь в db_sync.py): для каждого файла запоминается его
последнее ЗАМЕЧЕННОЕ содержимое и МОМЕНТ, когда мы его заметили - по
СОБСТВЕННЫМ часам читающего компьютера. Если значение файла изменилось
с прошлой проверки - пользователь точно активен прямо сейчас. Если не
изменилось - смотрим, сколько времени (по нашим же часам) прошло с
последнего замеченного изменения. Чужое время, записанное в файле,
вообще никогда не сравнивается напрямую с текущим временем читающего
компьютера.

Список "все, кто когда-либо подключался" (`known_users.txt`, функции
`_record_known_user`/`get_known_users`) - простой текстовый файл в той
же папке, ОБНОВЛЯЕТСЯ ВМЕСТЕ С presence, но НЕ хранится в самой
синхронизируемой базе данных - если бы это было частью базы (через
`bump_revision`), статус "синхронизировано" дёргался бы практически
постоянно, при каждом отклике присутствия, путая служебную телеметрию
с настоящими изменениями данных.

Метка присутствия удаляется (`db_sync.remove_presence()`) при
подтверждённом закрытии программы и при переключении в локальный/
полный офлайн режим - но это не критично для корректности: даже если
файл не удалён (сеть отвалилась в момент закрытия и т.п.), он просто
перестанет считаться "изменяющимся" и через ~30 секунд перестанет
засчитываться в count.

### 1.6. Защита от одновременного редактирования ОДНОЙ записи

Отдельная задача от общей синхронизации базы. У каждого насоса есть
поле `last_edited_at` (точность до секунды, обновляется при КАЖДОМ
`update_pump()`, независимо от того, какие именно поля менялись). При
открытии записи на редактирование это значение запоминается. При
попытке сохранения (`database.check_pump_unchanged()`) сверяется
текущее значение в базе с запомненным:
- совпадает - можно спокойно сохранять
- не совпадает - кто-то другой успел сохранить изменения в эту же
  запись, пока мы редактировали - показывается предупреждение с
  выбором (перезаписать/отменить), а не тихая перезапись
- запись не найдена - значит, была удалена - сохранить невозможно

Подключено в двух местах: основной диалог редактирования насоса
(`gui.py: on_edit_requested`) и редактирование истории/примечания
(`right_panel.py: manage_history`).

### 1.7. Уникальный идентификатор записи (uuid) и умное слияние

**Зачем нужен uuid, а не просто id или pump_number**: внутренний
автоинкрементный `id` может СОВПАСТЬ у двух записей, независимо
созданных на разных компьютерах (оба стартовали с одной и той же
версии базы, оба независимо что-то добавили). `pump_number` тоже не
годится - в системе намеренно допускаются законные дубли (один и тот
же физический насос тестировался повторно).

**КРИТИЧЕСКИЙ баг, который был обнаружен и исправлен** (см. историю
разработки): при добавлении поля `uuid` к уже существующим записям
(миграция в `database.init_db()`) изначально использовался
`uuid.uuid4()` - случайное значение. Поскольку миграция выполняется
НЕЗАВИСИМО на каждом компьютере, ОДНА И ТА ЖЕ запись (уже
синхронизированная между машинами до появления uuid) получала на
разных компьютерах РАЗНЫЕ случайные uuid. Из-за этого умное слияние не
находило совпадений вообще ни для одной старой записи и считало ВСЕ их
"новыми" - что приводило к полному дублированию базы при первой же
попытке слияния.

**Исправление**: `uuid.uuid5(uuid.NAMESPACE_OID, f"pump-{id}-{created_at}")`
- ДЕТЕРМИНИРОВАННАЯ функция (одинаковый вход всегда даёт одинаковый
результат, на любом компьютере). `id` и `created_at` для записи,
которая уже была синхронизирована (скопирована как часть общего файла
базы) между машинами, будут идентичны на всех копиях - поэтому
вычисленный uuid тоже совпадёт.

Дополнительно: в `database.init_db()` есть БЕЗУСЛОВНЫЙ (выполняется при
каждом запуске, но дёшево - обновляет только реально расходящиеся
значения) шаг, пересчитывающий uuid по этой же формуле для ВСЕХ
записей и исправляющий несовпадения - это самоисправляющийся механизм
для уже установленных копий программы, которые могли получить
неправильные (случайные) uuid от более ранней версии кода.

**Умное слияние** (`db_sync.smart_merge_push`) - срабатывает по выбору
пользователя, когда `push_local_to_network()` вернул `'network_ahead'`
(сеть изменилась, пока мы работали). Алгоритм:
1. Читает минимальный снимок насосов из сетевой базы: `{uuid: (last_edited_at, pump_number)}`
2. Сравнивает с полными локальными данными (`database.get_all_pumps_full_for_merge()`)
3. uuid есть локально, но нет в сети → новая запись, безопасно перенести
4. uuid есть и там, и там, но `last_edited_at` отличается → конфликт
   правки, автоматически НЕ переносится, сообщается пользователю по
   номеру насоса
5. Подтягивает сеть (`force_pull_network_to_local`)
6. Заново добавляет найденные "новые" записи (`add_pump(..., pump_uuid=...)`,
   СОХРАНЯЯ исходный uuid - это делает повторный запуск слияния
   безопасным: если процесс случайно выполнится дважды, uuid уже будет
   присутствовать в сети, и повторного дублирования не произойдёт)
7. Выгружает результат обратно в сеть (второй `shutil.copy2`, под тем
   же локом)

Правки существующих записей НЕ переносятся автоматически - сознательное
решение: для команды 5-7 человек с редкими правками одной и той же
записи, ручное разрешение конфликта проще и безопаснее, чем пытаться
угадывать "чья версия правильнее".

## 2. Пароли (auth.py)

Два независимых, но РАВНОЗНАЧНЫХ способа входа - подходит любой из них
(см. `auth.check_password()`):

1. **Основной пароль** - строковая константа `auth.DEFAULT_PASSWORD`
   прямо в коде. Меняется редактированием одной строки и пересборкой
   программы.
2. **Резервный (аварийный) пароль** - хранится ЛОКАЛЬНО на конкретном
   компьютере (НЕ через синхронизацию сети - иначе был бы доступен
   всем, а не только тем, кому положено), в скрытом файле
   `.pumpapp_sys/sys.dat` рядом с программой. Внутри - НЕ сам пароль, а
   его SHA-256 хеш (одностороннее преобразование - сравнение "хеш
   введённого" с "хешем сохранённого", без возможности восстановить
   исходный текст из хеша). Создаётся/меняется отдельным скриптом
   `generate_password_override.py` (не часть программы).

**Важно**: если резервный файл существует - работают ОБА варианта
одновременно (резервный ДОПОЛНЯЕТ основной, не заменяет его на
конкретном компьютере). Это сознательный выбор - резервный пароль
существует именно как аварийный вход на случай, если основной забыт, а
не как способ управления доступом на уровне отдельных компьютеров.

**Уровень защиты - намеренно минимальный** (по прямому запросу
заказчика): без соли, без ограничения количества попыток, без
блокировки после неудачных попыток. Задача - лёгкий барьер против
случайных действий, а не защита от целенаправленного взлома.

Разделение ролей "только просмотр / полное редактирование" достигается
НЕ через программу, а организационно - тем, кому нужен только
просмотр, просто не сообщается пароль.

## 3. Резервное копирование (db_sync.py)

Создаётся автоматически перед КАЖДОЙ операцией, которая перезаписывает
локальный файл (`force_pull_network_to_local`,
`check_and_sync_at_startup`). Имя файла включает ревизию
(`pumps_rev{ревизия}_{дата_время}.db`) - удобно для экрана
восстановления (видно конкретное состояние, а не просто дату).

Защита от дублирования: если копия с ТАКОЙ ЖЕ ревизией уже существует -
новая не создаётся (ревизия однозначно определяет состояние базы,
содержимое было бы идентично). Актуально, когда автоматическое
подтягивание и ручная кнопка N->L срабатывают почти одновременно без
реальных изменений базы между ними.

Хранится последние `_BACKUP_KEEP_COUNT` (30) копий, старые
автоматически удаляются.

## 4. Журнал изменений (database.py: change_log)

Отдельная таблица В САМОЙ базе данных (в отличие от presence/known_users
- этот журнал как раз ДОЛЖЕН быть частью синхронизируемых данных, чтобы
все видели одну и ту же историю). Заполняется автоматически внутри
`bump_revision()` при каждой операции записи. Хранит последние 30
записей (`_CHANGE_LOG_KEEP_COUNT`), старые автоматически вытесняются.

Описание действия включает имя пользователя (`getpass.getuser()`) в
начале строки - "Иванов: Добавлен насос №1234".

## 5. Анимации интерфейса - технические уроки

- **QPropertyAnimation + setStyleSheet() на каждом кадре** - дорогая
  операция (полный пересчёт CSS), вызванная 60 раз в секунду
  непрерывно (например, в мигающей подсветке кнопок), заметно
  конкурирует за процессорное время с другими анимациями (в частности,
  бегущей строкой уведомлений). Решение - округлять анимируемое
  значение до немногих дискретных уровней и применять дорогую операцию
  только когда округлённый уровень реально изменился
  (`left_panel.py: _ButtonGlowBlinker._set_intensity`).
- **Сетевые операции в основном потоке блокируют анимации** - вынесены
  в фоновый QThread (`gui.py: _RemoteCheckWorker`), результат
  передаётся обратно через pyqtSignal (Qt сам безопасно маршалит
  сигнал в основной поток).
- **Виджеты без окончательной геометрии в момент запуска анимации** -
  если анимация запускается ДО того, как окно показано и Qt обработал
  раскладку, расчёт стартовой позиции (например, бегущей строки) может
  использовать неверную (нулевую/дефолтную) ширину. Решение - отложенный
  вызов через `QTimer.singleShot()` с небольшой задержкой.

## 6. Что сознательно НЕ реализовано (и почему)

- **Полноценное автоматическое слияние правок одной записи** (не
  только добавлений) - при конфликте правки одной и той же записи
  умное слияние не пытается угадать "чья версия правильнее". Для
  команды 5-7 человек с редкими правками это разумный компромисс -
  усложнение ради редкого случая не оправдано.
- **Расширенные точки испытаний** (14 вместо обычных 8/9) - флажок
  `modifications.is_extended_template` в схеме базы уже есть, но сама
  логика чтения по смещённой раскладке ячеек Excel не реализована -
  отложено до появления реальной необходимости.
- **Плановое резервное копирование по расписанию** - не нужно при
  нечастом использовании базы (несколько раз в день, а не постоянно) -
  резервные копии и так создаются достаточно часто в момент
  синхронизации.
- **Полная очистка базы данных** (удаление всех насосов) - обсуждалась
  и была сознательно отклонена как слишком рискованная операция в
  условиях многопользовательской синхронизации (может стереть историю
  работы всей команды одним нажатием на одном компьютере).

## 8. Сортировка и постраничность списка насосов

### 8.1. Сортировка - на уровне SQL, а не средствами Qt

Клик по заголовку столбца сортирует ВСЮ базу (запрос с `ORDER BY`), а
не только уже загруженные строки. Изначально сортировка была сделана
через встроенный клиентский механизм Qt (`table.setSortingEnabled(True)`)
- он сортирует только строки, УЖЕ загруженные в таблицу (то есть только
текущую страницу), а не всю базу целиком. Переделано на: клик по
заголовку (`sectionClicked`) → пересчёт `ORDER BY` (`left_panel.py:
_get_order_by_sql`, столбец сопоставляется с полем через жёстко заданный
список - не пользовательский ввод, поэтому подстановка в SQL безопасна)
→ повторный запрос с новым `order_by`.

**Найденный и исправленный баг**: в `populate_table()` был остаточный
код от старой (клиентской) сортировки - `setSortingEnabled(True)` +
`sortByColumn(1, ...)` сразу после заполнения таблицы. Он: (а) заново
включал клиентскую сортировку Qt, перечёркивая серверную; (б)
принудительно пересортировывал по жёстко заданному столбцу (дате) -
из-за этого индикатор сортировки (стрелка на заголовке) всегда
возвращался на дату, а порядок строк на некоторых страницах путался
(клиентская сортировка Qt сравнивает ОТОБРАЖАЕМЫЙ ТЕКСТ ячеек, а не
исходные значения - для дат в формате ДД.ММ.ГГГГ это даёт неверный, не
хронологический порядок). Убран целиком.

**Порядок операций важен**: индикатор сортировки (`setSortIndicator`)
должен устанавливаться ПОСЛЕ перестроения таблицы (`display_pumps` →
`populate_table` → `_setup_table_columns` пересоздаёт заголовки через
`setHorizontalHeaderLabels`), а не до - иначе перестроение заголовков
сбрасывает уже выставленный индикатор.

Сортировка сбрасывается к значению по умолчанию (дата, по убыванию) при
переключении компактного/расширенного режима (разный набор и порядок
столбцов - индекс столбца из одного режима не имеет смысла в другом) и
при нажатии "Сбросить фильтры".

### 8.2. Постраничность - фиксированная ширина для избежания "прыжков"

Метка "Страница X из Y" и поле быстрого перехода имеют ЯВНО заданную
фиксированную ширину (`setFixedWidth`), а не просто минимальную
(`setMinimumWidth`) - при росте номеров страниц текст меняет длину
("Страница 1 из 5" короче "Страница 12 из 45"), и без фиксированной
ширины кнопка "вперёд" рядом с меткой заметно сдвигалась при
пролистывании. Та же логика применена к метке выбранного насоса в
статус-баре (`status_bar.py`) - раньше она полностью СКРЫВАЛАСЬ
(`setVisible(False)`) при отсутствии выбора, из-за чего левая часть
статус-бара схлопывалась до нуля и сдвигала центральную часть с
фильтрами; теперь всегда видима (просто с пустым текстом), с фиксированной
шириной и обрезанием текста многоточием (`QFontMetrics.elidedText`) на
случай очень длинного номера.

### 8.3. Постраничность режима "Дубли" - по границам групп

Раньше в режиме "Дубли" все найденные группы показывались одним
сплошным списком без разбивки на страницы. Переделано на постраничность,
но с ВАЖНЫМ требованием - группа (все протоколы одного насоса) никогда
не должна разрываться между двумя страницами. Реализовано через
`_group_duplicates()` (общая логика группировки, используется и для
подсчёта страниц, и для отображения) - сначала группируются ВСЕ
совпадающие записи, затем на страницу берётся заданное количество ГРУПП
целиком (`duplicates_groups_per_page = 6`), а не заданное количество
СТРОК. `next_page`/`prev_page`/`jump_to_page`/`update_pagination_label`
переведены на отдельный расчёт (`total_group_pages`) при активном
режиме дублей. Переключение режима "Дубли" сбрасывает текущую страницу
(`on_duplicates_toggled`) - иначе номер страницы одного режима мог бы
случайно перенестись в другой, где он не имеет смысла (разный принцип
разбивки).

### 8.4. Сортировка заказов - по числовой части, без учёта букв

И в фильтре, и в сводной статистике - `database._order_number_sort_key()`
извлекает цифры из номера заказа (`re.sub(r'\D', '', str(order_number))`)
и сортирует по убыванию этого числа, ИГНОРИРУЯ буквенный префикс.
Обычная сортировка в SQL (`ORDER BY order_number`) - это ТЕКСТОВОЕ
сравнение, которое расставляло бы, например, "К5666" и "5487" в порядке,
не соответствующем реальной величине числа. Сортировка перенесена в
Python (после выборки из SQL), поскольку "извлечь только цифры и
сравнить как число" не выражается портируемо на чистом SQL.

## 9. Графики сравнения дублей - геометрия и качество отображения

### 9.1. `_SCREEN_DPI` и `_GRAPH_LEGEND_FONT_SIZE` - подобраны опытным путём

Обе константы вынесены в начало `right_panel.py`, рядом друг с другом -
**значения заданы пользователем по итогам практической проверки и не
должны меняться без явного запроса** (на момент последнего обновления:
`_SCREEN_DPI = 130`, `_GRAPH_LEGEND_FONT_SIZE = 5`). При сохранении
графика в файл dpi временно повышается ещё сильнее и независимо
(`_FixedAspectToolbar.SAVE_DPI = 900`, тоже задано пользователем) - см.
9.3.

### 9.2. Урок про QSizePolicy.Expanding и figsize - ширина фигуры сама по
себе НЕ расширяет виджет

Была попытка сделать графики сравнения дублей шире (пропорция 16:10)
просто увеличив `figsize` у matplotlib `Figure`. Не сработало: canvas с
`QSizePolicy.Expanding` по обеим осям просто СЖИМАЕТСЯ под уже имеющуюся
ширину контейнера, независимо от того, что задано в figsize - это влияет
только на исходное соотношение сторон ПРИ ОТРИСОВКЕ, но не заставляет
виджет физически стать шире панели. Чтобы графика реально стала шире
(и, если нужно, вызывала горизонтальную прокрутку) - контейнеру нужно
явно задать `setMinimumWidth()` (реализовано как параметр `min_width` у
`_make_graph_widget()`) в пикселях, превышающих обычную ширину панели.

### 9.3. Урок про рост figsize по высоте - утягивает соседние виджеты

Более ранняя попытка "не обрезать легенду" заключалась в динамическом
увеличении высоты figsize вместе с числом сравниваемых дублей (больше
дублей → больше строк легенды → выше фигура). Это работало для самой
легенды, но ломало общий layout: контейнер графика без явно заданной
фиксированной высоты (`_make_graph_widget(fig, height=...)`) просто рос
вместе с figsize, утягивая за собой ВЕСЬ layout (включая соседние
таблицы, у которых заметно растягивались шапки). Откачено полностью -
размер фигуры снова фиксирован (не растёт с числом дублей), недостающее
место под легенду решается ТОЛЬКО уменьшенным шрифтом
(`_GRAPH_LEGEND_FONT_SIZE`), без изменения геометрии.

### 9.4. Перенос длинного текста в таблице сравнения герметичности

При сравнении 3 и более дублей таблица результатов проверки
герметичности (`_create_comparison_seal_table`) может выйти за пределы
видимой области ПО ШИРИНЕ - `resizeColumnsToContents()` растягивает
каждую колонку под самый длинный однострочный текст ("Присутствуют в
допускаемой степени", ~35 символов), и при 3+ колонках (по одной на
дубль) суммарная ширина превышает панель, а собственной горизонтальной
прокрутки у ВЛОЖЕННОЙ таблицы нет. Решение - при 3+ дублях именно это
конкретное значение переносится на 2 строки (`\n` в тексте
QTableWidgetItem) - перенос "тратит" высоту вместо ширины. Раскраска
фона ячейки (жёлтый/красный) использует ИСХОДНОЕ, не перенесённое
значение - изменение текста отображения не затрагивает логику
сравнения с нормативом.

## 10. Полосы прокрутки в фирменном стиле

### 10.1. `_GlowScrollBar` (left_panel.py) - собственная отрисовка,
работает в обеих ориентациях

Подкласс `QScrollBar` с полностью своим `paintEvent` - QSS не умеет ни
плавную анимацию ширины, ни "бегущую" подсветку. В состоянии покоя -
тонкая линия акцентного цвета; при наведении/прокрутке колесом плавно
расширяется симметрично в обе стороны от центра, с настоящим свечением
(ярче по центру бегунка, гаснет к его краям). Изначально был жёстко
привязан к `Qt.Vertical` - обобщён под параметр `orientation`, вся
геометрия в `paintEvent` считается через `self.orientation()`, а не
через отдельно хранимый флаг.

### 10.2. Два разных способа применения - overlay и замена штатной
полосы - выбор зависит от того, что ЕЩЁ рисуется в том же viewport

**Overlay** (правая панель, `_OverlayScrollArea`) - `_GlowScrollBar`
создаётся как независимый child-виджет `viewport()`, ПОВЕРХ содержимого,
без резервирования места в layout (встроенные полосы Qt отключены через
`ScrollBarAlwaysOff`). Синхронизация значения/диапазона - вручную, через
сигналы `rangeChanged`/`valueChanged` в обе стороны. Работает без
проблем, поскольку в правой панели больше ничего не претендует на
z-порядок поверх viewport.

**Замена штатной полосы** (таблица списка насосов, `left_panel.py`) -
`table.setVerticalScrollBar(_GlowScrollBar(table))`. **Overlay-подход
для таблицы был опробован и провалился**: у таблицы уже есть собственная
система подсветки выделения/наведения строк (`_hover_overlay`/
`_selection_overlay`), которая ТОЖЕ рисуется поверх viewport и
периодически "поднимается" в z-порядке (`raise_()`) при наведении/
выделении - оверлей-полоса прокрутки то и дело оказывалась перекрыта и
переставала быть кликабельной. Замена через штатный API Qt
(`setVerticalScrollBar`) полностью решает проблему - полоса занимает своё
ОБЫЧНОЕ, зарезервированное место (не поверх viewport), поэтому конфликта
по z-порядку в принципе не возникает, а Qt сам берёт на себя ВСЮ
синхронизацию значения/диапазона (никаких сигналов подключать вручную
не нужно - в отличие от overlay-подхода).

**Практический вывод на будущее**: если понадобится ещё где-то
"фирменная" полоса прокрутки поверх виджета с собственной, уже
существующей логикой отрисовки/z-порядка (не простого статичного
содержимого) - начинать сразу со способа "замена штатной полосы" (`set*ScrollBar()`),
а не с overlay.

### 10.3. Прокрутка средней кнопкой мыши - реализована и убрана

Была попытка добавить grab-scroll (зажать колесо мыши, потянуть в любую
сторону) через `eventFilter` на viewport правой панели. Пользователь
счёл реализацию неудачной на практике - убрана целиком, оставлены
только сами полосы прокрутки без альтернативного способа прокрутки
мышью.

## 11. Тема оформления - систематическая проверка на "наследие тёмной темы"

Несколько диалогов содержали жёстко заданный цвет `#e8eaed` (светлый
текст, предназначенный для тёмной темы) БЕЗ проверки `is_light_theme()`

от темы - там фиксированный тёмный цвет иконки корректен и трогать не
нужно).

**Практический урок**: при поиске подобных проблем полезно грепать по
конкретным hex-кодам (`#e8eaed`, `#2b2d31` и т.п.) внутри ОДНОГО диалога/
класса и вручную проверять каждое вхождение - является ли оно частью
осознанно "всегда тёмного" элемента (например, заголовок таблицы с
намеренно тёмным фоном, где светлый текст корректен в любой теме) или
действительно нуждается в проверке темы.

## 12. Диалоги - положение крестика закрытия и перенос длинного текста

Несколько итераций отладки того, почему крестик закрытия в
`GlowMessageDialog` иногда оказывался не у правого края, а ближе к
середине окна:

1. Расчёт `self.glow_frame.width()` для позиционирования крестика
   происходил ДО того, как `adjustSize()` действительно завершил
   пересчёт геометрии дочерних виджетов - добавлен `QApplication.processEvents()`
   между шагами.
2. Повторное позиционирование добавлено также в `showEvent()` (не
   только в `_lock_size()`, вызываемой из `__init__`) - на случай, если
   расчёт на момент `__init__` был неточен для содержимого с ещё не до
   конца определившейся шириной (например, список с прокруткой).
3. **Наиболее вероятная настоящая причина** - сообщения об ошибках,
   куда подставлялся СЫРОЙ текст исключения (`f"...{e}"`), могли
   содержать ДЛИННЫЙ СЕТЕВОЙ ПУТЬ БЕЗ ПРОБЕЛОВ (например, полный UNC-путь
   к недоступному файлу). Перенос текста (`setWordWrap`) физически не
   может разбить строку без пробелов на несколько строк - содержимое
   вылезало за пределы заданной ширины, окно раздувалось до
   непредсказуемого размера, из-за чего расчёт положения крестика "плыл".
   **Исправление - на уровне ИСТОЧНИКА данных, а не на уровне диалога**:
   из всех сообщений в `db_sync.py` убран сырой текст исключения,
   заменён на обобщённые формулировки без путей ("сеть, возможно, только
   что стала недоступна").
4. Ширина метки сообщения (`msg_label`) переведена на расчёт по
   реальным метрикам шрифта (`QFontMetrics.horizontalAdvance`) вместо
   фиксированной ширины - короткие сообщения ("Нечего выгружать")
   остаются компактными, длинные по-прежнему переносятся в разумных
   границах (до 380px).

**Общий практический вывод**: НЕ подставлять сырой текст исключений
(`str(e)`) напрямую в пользовательские сообщения, если он потенциально
может содержать длинные пути/URL без пробелов - разбирать текст ошибки
и формулировать обобщённое сообщение самостоятельно.

## 13. Наполнение реальными данными - находки при разборе входного JSON

При переносе ~200 реальных записей (`populate_real_data.py`, разовый
скрипт, не часть программы) обнаружено и обработано:

- **Дата иногда в формате "дата1(дата2)"** - например,
  `"11.12.2025(20.01.2026)"`. Означало основную/повторную дату;
  подтверждено использовать именно дату В СКОБКАХ. Разбирается через
  `re.search(r'\(([\d.]+)\)', date_str)` - если совпадение есть, дальше
  парсится именно найденная подстрока.
- **Регистр и формулировки полей герметичности не совпадали дословно**
  с точными вариантами выпадающих списков программы (`dialogs.py:
  _LEAK_OPTIONS`/`_OIL_OPTIONS`) - все входные значения приведены к
  нижнему регистру и сопоставлены явными словарями (`LEAK_MAP`/`OIL_MAP`
  в скрипте наполнения). Одно значение оказалось опечаткой/иной
  формулировкой того же смысла ("образования в чрезмерном объеме" →
  "Присутствуют в чрезмерном объёме") - сопоставлено вручную, не
  автоматическим правилом.
- **uuid у существующих (перенесённых скриптом) записей** - генерируется
  автоматически тем же детерминированным способом, что и миграция (см.
  1.7) - `add_pump()` без явного `pump_uuid` сама вызывает `uuid.uuid4()`
  при создании. Поскольку это НОВЫЕ записи (не переносимые между уже
  синхронизированными копиями), случайный uuid здесь корректен и не
  создаёт риска дублирования при умном слиянии - тот баг был специфичен
  именно для ЗАДНИМ ЧИСЛОМ присваиваемых uuid уже существовавшим записям.
- **Скрипт сверяет вердикт из файла с расчётом программы**
  (`utils.compute_verdict_and_sealed`) и выводит расхождения в конце -
  не блокирует перенос (данные из файла считаются источником истины по
  договорённости), но даёт возможность проверить нормативы модификации
  на реальных данных постфактум.
- **После наполнения `change_log` целенаправленно очищается**
  (`DELETE FROM change_log`) - массовое наполнение через прямые вызовы
  `add_pump()` в скрипте технически ТОЖЕ пишет в журнал (через
  `bump_revision()` внутри `add_pump`), но итоговая, отгружаемая с
  установщиком база не должна содержать этих служебных записей.

## 14. Код-ревью всего проекта - находки и системные уроки

После накопления большого объёма правок был проведён построчный обзор
всех 17 файлов проекта (не только новых функций, но и уже давно
работающего кода). Ключевые находки:

### 14.1. Уязвимость при восстановлении из резервной копии + выгрузке

`push_local_to_network()` раньше сравнивала локальную ревизию ТОЛЬКО с
запомненной точкой последней синхронизации (`last_sync_revision`), а не
с текущей сетевой ревизией напрямую. Если пользователь восстанавливал
локальную базу из БОЛЕE СТАРОЙ резервной копии (локальная ревизия
становится МЕНЬШЕ сетевой), а `last_sync_revision` при этом случайно
совпадала с текущей сетевой - обе проверки проходили, и устаревшие
данные могли молча перезаписать сетевую базу.

**Исправление**: сравнение переведено на прямое `local_revision` vs
ТЕКУЩАЯ `network_revision` (читается заново при каждой попытке
выгрузки), без опоры на `last_sync_revision` для этой конкретной
проверки. Устраняет уязвимость независимо от того, ПОЧЕМУ локальная
ревизия оказалась меньше сетевой.

### 14.2. Системная ошибка нормализации номера заказа - в 8 местах

Один и тот же фрагильный паттерн (`str(x).replace('.0', '')`) был
независимо скопирован в 8 разных местах по всему проекту (включая саму
функцию-обёртку `utils.format_order_number()`, которая должна была быть
единой точкой правды). Проблема: `.replace('.0', '')` убирает ЛЮБОЕ
вхождение подстроки ".0" где угодно в строке, а не только хвостовой
float-артефакт от Excel/pandas - настоящий номер заказа вроде "5.087"
превращался в "587".

**Исправление**: единая функция `utils.format_order_number()`,
использующая `re.sub(r'\.0$', '', s)` - убирает ТОЛЬКО буквальное ".0"
СТРОГО в конце строки. Тот же принцип продублирован в
`database.add_order()` (независимый слой данных, сознательно не
импортирует `utils`). Все 7 остальных мест по проекту (`gui.py` ×2,
`left_panel.py`, `right_panel.py`, `dialogs.py`, `excel_importer.py`)
переведены на вызов этой единой функции вместо собственных копий.

**Практический урок**: если один и тот же алгоритм нормализации данных
нужен в нескольких местах интерфейса - явно выносить в `utils.py` СРАЗУ,
а не полагаться на копирование "на глаз" по мере надобности.

### 14.3. `count_pumps()` не учитывала фильтр дублей

Функция была задумана как точная копия условий `get_all_pumps()`, но
условие `only_duplicates` при копировании забыли перенести. Счётчик
"Показано записей" в режиме дублей показывал общее количество всех
подходящих насосов, а не только тех, что входят в группы дублей.
Сама постраничная навигация при этом работала верно (использует
отдельный расчёт `total_group_pages`) - страдал только текст счётчика.

### 14.4. Мёртвый код - несколько независимых находок

- `database.py: get_order_by_id()` - активная версия с остаточными
  `print("[DEBUG ...]")`, а прямо над ней - закомментированная чистая
  версия той же функции. Убрано.
- `gui.py: update_status()` - закомментированная устаревшая версия
  функции прямо над активной. Убрано.
- `gui.py: on_edit_requested()` - лишнее, противоречащее сообщение
  "Примечание обновлено" сразу после "Изменений не обнаружено" - остаток
  от более ранней версии функции. Убрано.
- `dialogs.py: EditProtocolDialog` - целый класс, нигде не
  инстанцируется по всему проекту (вытеснен связкой `EditPumpDialog` +
  `EditHistoryDialog`), к тому же в другом визуальном стиле (обычный
  `QDialog`, не фирменный `_GlowDialog`). Убран целиком.
- `styles.py: get_horizontal_scrollbar_style()` - QSS для горизонтальной
  полосы прокрутки правой панели, переставший к чему-либо применяться

### 14.5. Оптимизация - `update_status()`

Вызывается очень часто (при каждом выборе записи, правке, смене
фильтра), но тянула из базы ВСЕ записи целиком (включая коррелированный
подзапрос подсчёта дублей на каждую строку) только ради подсчёта двух
чисел. Заменено на лёгкий агрегатный SQL-запрос
(`database.get_pump_counts()` - `SELECT COUNT(*), SUM(CASE WHEN
verdict = 'годен' THEN 1 ELSE 0 END)`).

### 14.6. Технический урок - `shutil.copy2()` и время файла резервных копий

`shutil.copy2()` копирует не только содержимое файла, но и его время
изменения (mtime) С ИСХОДНИКА. Список резервных копий сортируется по
этому времени (`os.path.getmtime`) - если исходная локальная база сама
недавно была ВОССТАНОВЛЕНА из более старой резервной копии (та же
`copy2()` при восстановлении переносит СТАРОЕ время на локальный файл),
это старое время "протягивалось" дальше на каждую следующую резервную
копию, сделанную с этой базы - копия, созданная только что, могла
показываться в списке НЕ как самая новая.

**Исправление**: после каждого `shutil.copy2()`, создающего файл
резервной копии (не восстанавливающего рабочую базу - там время
исходного файла неважно), добавлен явный `os.utime(dest_path, None)` -
принудительно выставляет ТЕКУЩЕЕ время на файл копии, независимо от
времени исходника.

### 14.7. Технический урок - окончания строк (CRLF/LF) при передаче файлов

Все файлы проекта используют Windows-стиль окончания строк (`\r\n`).
Инструменты редактирования, использованные в ходе этой работы, при
записи файла с нуля используют `\n` (Unix-стиль) по умолчанию - при
точечных правках через строковую замену это не создаёт проблем (меняется
только сама затронутая строка), но при СОЗДАНИИ файла заново (например,
когда пришлось восстанавливать `utils.py` из присланного текста) ВЕСЬ
файл получает `\n` вместо `\r\n`. Из-за этого сравнение (`diff`) с
оригиналом показывает "изменена каждая строка", хотя реально изменилось
несколько - создаёт ложное впечатление огромного объёма правок и мешает
человеку увидеть, что РЕАЛЬНО поменялось в его собственной системе
контроля версий.

**Практический урок**: при передаче файлов пользователю на Windows-
проекте с `\r\n` - всегда проверять/приводить окончания строк перед
финальной отправкой (`content.replace(b'\r\n', b'\n').replace(b'\n', b'\r\n')`
гарантированно нормализует к `\r\n`, независимо от того, что было в
процессе редактирования).

## 15. Умное слияние vs полная замена сети - расширение решения по `network_ahead`

По итогам практического использования умного слияния (см. 1.7) выявлен
реальный сценарий, для которого одного только слияния недостаточно:
пользователь восстановил локальную базу из старой резервной копии,
затем ВЫГРУЗИЛ её в сеть через умное слияние - сеть при этом
"разрослась" лишними, уже ненужными записями (слияние добавляет то, что
есть локально и отсутствует в сети - оно не удаляет ничего). Чтобы
откатить И сетевую базу тоже (не просто слить, а именно ЗАМЕНИТЬ),
понадобился второй, самостоятельный механизм.

### 15.1. `db_sync.force_push_local_to_network()`

Полная, безусловная замена сетевой базы локальной копией - обычное
копирование файла целиком (`shutil.copy2`), НЕ слияние. Любые записи,
которые есть в сети, но отсутствуют в локальной копии, ПОСЛЕ ЭТОЙ
ОПЕРАЦИИ ПЕРЕСТАЮТ СУЩЕСТВОВАТЬ в сети - это осознанно, ради того самого
сценария "нужно удалить из сети то, чего больше нет локально". Перед
перезаписью автоматически создаётся резервная копия ТЕКУЩЕЙ сетевой базы
(`_backup_network_copy()`, префикс файла `pumps_network_`) - если что-то
из удалённого впоследствии понадобится, можно восстановить вручную.

### 15.2. `NetworkAheadChoiceDialog` - единый диалог с тремя вариантами

Изначально выбор между умным слиянием и полной заменой был реализован
цепочкой из двух последовательных `confirm()`-диалогов (отказ от первого
предлагал второй) - на практике оказалось легко перепутать, какой
именно вариант выбираешь при отказе от умного слияния (не всем было
очевидно, что дальше предложат полную замену, а не просто отмену).
Переделано на ОДИН диалог с тремя кнопками сразу (по образцу уже
существующего `PrintChoiceDialog` - тот же паттерн `self.choice` +
`_choose(value)`), с пояснением под каждой кнопкой, что именно она
сделает.

### 15.3. Раздельное хранение резервных копий - локальные и сетевые

`_cleanup_old_backups()` хранит локальные (`pumps_rev...`,
`pumps_before_sync_...`) и сетевые (`pumps_network_...`) копии в ДВУХ
независимых пулах, каждый со своим лимитом (`_BACKUP_KEEP_COUNT`).
Причина: сетевые копии создаются РЕДКО (только при осознанной полной
замене), а локальные - часто (при каждой обычной синхронизации) - в
общем пуле частые локальные быстро вытеснили бы редкие, но более ценные
сетевые.

## 16. Резервное копирование по требованию пользователя

### 16.1. `db_sync.create_manual_backup()`

Принудительное создание резервной копии - по явному нажатию кнопки
"Сохранить копию" (левая панель, рядом с "Выгрузить"). В ОТЛИЧИЕ от
автоматических копий (`_backup_local_copy()`, пропускается, если копия
с текущей ревизией уже существует - см. 3), эта функция ВСЕГДА создаёт
новый файл, даже если копия с такой же ревизией уже есть - пользователь
должен точно знать, что копия сохранена именно СЕЙЧАС, по его
собственному явному действию, а не гадать, произошло ли это
автоматически. Имя файла содержит маркер `_manual_` - в списке
восстановления такие копии помечаются "· создано вручную".

### 16.2. `db_sync.delete_backup()` и подсчёт количества насосов

Диалог "Восстановить из резервной копии" дополнен кнопкой удаления
выбранной копии (с подтверждением) и отображением количества насосов
внутри каждой копии (`_count_pumps_in_backup()` - краткое, только для
чтения, открытие каждого файла ради одного агрегатного запроса
`SELECT COUNT(*) FROM pumps`) - помогает отличить копии друг от друга не
только по дате/ревизии, но и по объёму данных, особенно полезно именно
при путанице вида "какая из копий была ДО того, как я случайно всё
почистил".

### 16.3. Кнопка - адаптивная под режим просмотра

По тому же принципу, что и кнопка "Выгрузить" - в компактном режиме
списка только иконка (SVG, перекрашивается через `icon_utils.tinted_icon`),
в расширенном - иконка плюс подпись "Сохранить текущую копию БД".
Ширина и внутренние отступы (padding) переключаются вместе с режимом
в `toggle_view()` - отдельный, более просторный QSS для расширенного
состояния (длинный текст нуждается в бо́льших боковых отступах, чем
узкая кнопка-иконка).
