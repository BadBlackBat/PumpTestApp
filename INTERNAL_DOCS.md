# PumpTestApp - внутренняя документация (логика и алгоритмы)

Этот файл - НЕ для конечных пользователей программы. Он описывает, как
устроена логика внутри кода: почему принимались те или иные решения,
как работают алгоритмы синхронизации, защиты и паролей. Предназначен
для того, кто будет дальше дорабатывать/поддерживать программу.

---

## 1. Архитектура многопользовательской работы

### 1.1. Общий принцип

Программа **всегда** читает и пишет только в свою **локальную** копию
базы данных (`database.get_active_db_path()` безусловно возвращает
`db_settings.get_local_db_path()`, даже когда включён сетевой режим).
Сетевой файл (`db_settings.get_network_db_path()`) - это просто общая
точка обмена, к которой программа обращается только в конкретные,
явные моменты:

1. При старте программы - сверка версий, копирование при необходимости
   (`db_sync.check_and_sync_at_startup`, вызывается из `main.py`)
2. Периодически во время работы (раз в 8 секунд, в фоновом потоке) -
   проверка изменений + присутствие пользователей
   (`gui.py: _RemoteCheckWorker`, `db_sync.check_for_remote_changes`)
3. По кнопке "Выгрузить" - копирование локальной базы в сеть
   (`db_sync.push_local_to_network`)
4. По кнопке "N -> L" - принудительное копирование сети в локальную базу
   (`db_sync.force_pull_network_to_local`)

Такая архитектура была выбрана вместо прямой работы с сетевым файлом
(SQLite по сети ненадёжен для одновременной записи с нескольких машин),
и вместо неё же естественно ложится офлайн-режим - "работаю локально,
пока не нажму кнопку" работает одинаково что при рабочей сети, что при
её полном отсутствии.

### 1.2. Ревизия базы данных (db_meta.revision)

Каждая операция записи (`database.bump_revision()`) увеличивает
ревизию. Формат: `ГГММДД * 1000 + счётчик_за_день` (год идёт ПЕРВЫМ,
не как в привычном ДД.ММ.ГГ отображении) - это критично для того, чтобы
обычное числовое сравнение "какая ревизия больше" совпадало с
хронологическим порядком. Если бы день шёл первым (как в отображении),
сравнение ломалось бы на стыке месяцев/годов (например, 01.01.27 как
число оказалось бы МЕНЬШЕ, чем 31.12.26).

Отображение для человека - `database.format_revision_display()`,
разбирает число обратно и показывает в привычном ДДММГГ.счётчик виде.

### 1.3. Точка синхронизации (db_settings.last_sync_revision)

Отдельное значение (не путать с ревизией самой базы!) - локальная
ревизия НА МОМЕНТ, когда локальная копия последний раз точно совпадала
с сетью (после pull или после успешного push). Статус
"синхронизировано"/"есть изменения" (`db_sync.is_synced()`) - это
просто сравнение текущей локальной ревизии с этой точкой.

Важный нюанс в `check_and_sync_at_startup()`: если локальная ревизия
БОЛЬШЕ сетевой (у пользователя есть локальные правки, которые ещё не
были в сети - например, накопленные до включения сетевого режима),
точка синхронизации НЕ обновляется - иначе статус ошибочно показал бы
"синхронизировано", хотя на самом деле есть неотправленные изменения.

### 1.4. Лок-файл (db_lock.py)

Эксклюзивный лок-файл (`<сетевой_путь>.lock`) - создаётся ТОЛЬКО на
момент самой записи в сетевой файл (доли секунды: скопировать
локальный файл поверх сетевого), не на всё время редактирования в
диалоге. Используется в `push_local_to_network()`,
`smart_merge_push()`.

**Критический урок из отладки**: нельзя полагаться на mtime сетевой
папки (метаданные файловой системы) для определения "протух ли лок" -
на реальной сетевой шаре mtime отставал от локальных часов клиента на
~223 секунды. Вместо этого время создания лока хранится ВНУТРИ его
содержимого (`хост:пользователь:время`), и проверка возраста лока
сравнивает это записанное время с ТЕКУЩИМ временем того же самого
процесса, который его читает - то есть всегда с самим собой, а не
полагается на чужие метаданные.

### 1.5. Присутствие пользователей (db_sync.py: update_presence,
get_active_user_count)

Каждый компьютер раз в 8 секунд обновляет свой файл-метку
(`<сетевая_папка>/active_users/<имя_пользователя>.presence`) с текущим
временем внутри. Другие компьютеры читают эти файлы и считают, сколько
из них "свежие".

**Критический урок из отладки**: НЕЛЬЗЯ сравнивать время, записанное
ОДНИМ компьютером, с текущим временем ДРУГОГО - часы разных машин в
сети не обязательно синхронизированы (на практике наблюдалось
расхождение, из-за которого один компьютер всегда видел чужие метки
как "протухшие"). Правильный подход - `_presence_seen_cache` (модуль-
уровневый словарь в db_sync.py): для каждого файла запоминается его
последнее ЗАМЕЧЕННОЕ содержимое и МОМЕНТ, когда мы его заметили - по
СОБСТВЕННЫМ часам читающего компьютера. Если значение файла изменилось
с прошлой проверки - пользователь точно активен прямо сейчас. Если не
изменилось - смотрим, сколько времени (по нашим же часам) прошло с
последнего замеченного изменения. Чужое время, записанное в файле,
вообще никогда не сравнивается напрямую с текущим временем читающего
компьютера.

Список "все, кто когда-либо подключался" (`known_users.txt`, функции
`_record_known_user`/`get_known_users`) - простой текстовый файл в той
же папке, ОБНОВЛЯЕТСЯ ВМЕСТЕ С presence, но НЕ хранится в самой
синхронизируемой базе данных - если бы это было частью базы (через
`bump_revision`), статус "синхронизировано" дёргался бы практически
постоянно, при каждом отклике присутствия, путая служебную телеметрию
с настоящими изменениями данных.

Метка присутствия удаляется (`db_sync.remove_presence()`) при
подтверждённом закрытии программы и при переключении в локальный/
полный офлайн режим - но это не критично для корректности: даже если
файл не удалён (сеть отвалилась в момент закрытия и т.п.), он просто
перестанет считаться "изменяющимся" и через ~30 секунд перестанет
засчитываться в count.

### 1.6. Защита от одновременного редактирования ОДНОЙ записи

Отдельная задача от общей синхронизации базы. У каждого насоса есть
поле `last_edited_at` (точность до секунды, обновляется при КАЖДОМ
`update_pump()`, независимо от того, какие именно поля менялись). При
открытии записи на редактирование это значение запоминается. При
попытке сохранения (`database.check_pump_unchanged()`) сверяется
текущее значение в базе с запомненным:
- совпадает - можно спокойно сохранять
- не совпадает - кто-то другой успел сохранить изменения в эту же
  запись, пока мы редактировали - показывается предупреждение с
  выбором (перезаписать/отменить), а не тихая перезапись
- запись не найдена - значит, была удалена - сохранить невозможно

Подключено в двух местах: основной диалог редактирования насоса
(`gui.py: on_edit_requested`) и редактирование истории/примечания
(`right_panel.py: manage_history`).

### 1.7. Уникальный идентификатор записи (uuid) и умное слияние

**Зачем нужен uuid, а не просто id или pump_number**: внутренний
автоинкрементный `id` может СОВПАСТЬ у двух записей, независимо
созданных на разных компьютерах (оба стартовали с одной и той же
версии базы, оба независимо что-то добавили). `pump_number` тоже не
годится - в системе намеренно допускаются законные дубли (один и тот
же физический насос тестировался повторно).

**КРИТИЧЕСКИЙ баг, который был обнаружен и исправлен** (см. историю
разработки): при добавлении поля `uuid` к уже существующим записям
(миграция в `database.init_db()`) изначально использовался
`uuid.uuid4()` - случайное значение. Поскольку миграция выполняется
НЕЗАВИСИМО на каждом компьютере, ОДНА И ТА ЖЕ запись (уже
синхронизированная между машинами до появления uuid) получала на
разных компьютерах РАЗНЫЕ случайные uuid. Из-за этого умное слияние не
находило совпадений вообще ни для одной старой записи и считало ВСЕ их
"новыми" - что приводило к полному дублированию базы при первой же
попытке слияния.

**Исправление**: `uuid.uuid5(uuid.NAMESPACE_OID, f"pump-{id}-{created_at}")`
- ДЕТЕРМИНИРОВАННАЯ функция (одинаковый вход всегда даёт одинаковый
результат, на любом компьютере). `id` и `created_at` для записи,
которая уже была синхронизирована (скопирована как часть общего файла
базы) между машинами, будут идентичны на всех копиях - поэтому
вычисленный uuid тоже совпадёт.

Дополнительно: в `database.init_db()` есть БЕЗУСЛОВНЫЙ (выполняется при
каждом запуске, но дёшево - обновляет только реально расходящиеся
значения) шаг, пересчитывающий uuid по этой же формуле для ВСЕХ
записей и исправляющий несовпадения - это самоисправляющийся механизм
для уже установленных копий программы, которые могли получить
неправильные (случайные) uuid от более ранней версии кода.

**Умное слияние** (`db_sync.smart_merge_push`) - срабатывает по выбору
пользователя, когда `push_local_to_network()` вернул `'network_ahead'`
(сеть изменилась, пока мы работали). Алгоритм:
1. Читает минимальный снимок насосов из сетевой базы: `{uuid: (last_edited_at, pump_number)}`
2. Сравнивает с полными локальными данными (`database.get_all_pumps_full_for_merge()`)
3. uuid есть локально, но нет в сети → новая запись, безопасно перенести
4. uuid есть и там, и там, но `last_edited_at` отличается → конфликт
   правки, автоматически НЕ переносится, сообщается пользователю по
   номеру насоса
5. Подтягивает сеть (`force_pull_network_to_local`)
6. Заново добавляет найденные "новые" записи (`add_pump(..., pump_uuid=...)`,
   СОХРАНЯЯ исходный uuid - это делает повторный запуск слияния
   безопасным: если процесс случайно выполнится дважды, uuid уже будет
   присутствовать в сети, и повторного дублирования не произойдёт)
7. Выгружает результат обратно в сеть (второй `shutil.copy2`, под тем
   же локом)

Правки существующих записей НЕ переносятся автоматически - сознательное
решение: для команды 5-7 человек с редкими правками одной и той же
записи, ручное разрешение конфликта проще и безопаснее, чем пытаться
угадывать "чья версия правильнее".

## 2. Пароли (auth.py)

Два независимых, но РАВНОЗНАЧНЫХ способа входа - подходит любой из них
(см. `auth.check_password()`):

1. **Основной пароль** - строковая константа `auth.DEFAULT_PASSWORD`
   прямо в коде. Меняется редактированием одной строки и пересборкой
   программы.
2. **Резервный (аварийный) пароль** - хранится ЛОКАЛЬНО на конкретном
   компьютере (НЕ через синхронизацию сети - иначе был бы доступен
   всем, а не только тем, кому положено), в скрытом файле
   `.pumpapp_sys/sys.dat` рядом с программой. Внутри - НЕ сам пароль, а
   его SHA-256 хеш (одностороннее преобразование - сравнение "хеш
   введённого" с "хешем сохранённого", без возможности восстановить
   исходный текст из хеша). Создаётся/меняется отдельным скриптом
   `generate_password_override.py` (не часть программы).

**Важно**: если резервный файл существует - работают ОБА варианта
одновременно (резервный ДОПОЛНЯЕТ основной, не заменяет его на
конкретном компьютере). Это сознательный выбор - резервный пароль
существует именно как аварийный вход на случай, если основной забыт, а
не как способ управления доступом на уровне отдельных компьютеров.

**Уровень защиты - намеренно минимальный** (по прямому запросу
заказчика): без соли, без ограничения количества попыток, без
блокировки после неудачных попыток. Задача - лёгкий барьер против
случайных действий, а не защита от целенаправленного взлома.

Разделение ролей "только просмотр / полное редактирование" достигается
НЕ через программу, а организационно - тем, кому нужен только
просмотр, просто не сообщается пароль.

## 3. Резервное копирование (db_sync.py)

Создаётся автоматически перед КАЖДОЙ операцией, которая перезаписывает
локальный файл (`force_pull_network_to_local`,
`check_and_sync_at_startup`). Имя файла включает ревизию
(`pumps_rev{ревизия}_{дата_время}.db`) - удобно для экрана
восстановления (видно конкретное состояние, а не просто дату).

Защита от дублирования: если копия с ТАКОЙ ЖЕ ревизией уже существует -
новая не создаётся (ревизия однозначно определяет состояние базы,
содержимое было бы идентично). Актуально, когда автоматическое
подтягивание и ручная кнопка N->L срабатывают почти одновременно без
реальных изменений базы между ними.

Хранится последние `_BACKUP_KEEP_COUNT` (30) копий, старые
автоматически удаляются.

## 4. Журнал изменений (database.py: change_log)

Отдельная таблица В САМОЙ базе данных (в отличие от presence/known_users
- этот журнал как раз ДОЛЖЕН быть частью синхронизируемых данных, чтобы
все видели одну и ту же историю). Заполняется автоматически внутри
`bump_revision()` при каждой операции записи. Хранит последние 30
записей (`_CHANGE_LOG_KEEP_COUNT`), старые автоматически вытесняются.

Описание действия включает имя пользователя (`getpass.getuser()`) в
начале строки - "Иванов: Добавлен насос №1234".

## 5. Анимации интерфейса - технические уроки

- **QPropertyAnimation + setStyleSheet() на каждом кадре** - дорогая
  операция (полный пересчёт CSS), вызванная 60 раз в секунду
  непрерывно (например, в мигающей подсветке кнопок), заметно
  конкурирует за процессорное время с другими анимациями (в частности,
  бегущей строкой уведомлений). Решение - округлять анимируемое
  значение до немногих дискретных уровней и применять дорогую операцию
  только когда округлённый уровень реально изменился
  (`left_panel.py: _ButtonGlowBlinker._set_intensity`).
- **Сетевые операции в основном потоке блокируют анимации** - вынесены
  в фоновый QThread (`gui.py: _RemoteCheckWorker`), результат
  передаётся обратно через pyqtSignal (Qt сам безопасно маршалит
  сигнал в основной поток).
- **Виджеты без окончательной геометрии в момент запуска анимации** -
  если анимация запускается ДО того, как окно показано и Qt обработал
  раскладку, расчёт стартовой позиции (например, бегущей строки) может
  использовать неверную (нулевую/дефолтную) ширину. Решение - отложенный
  вызов через `QTimer.singleShot()` с небольшой задержкой.

## 6. Что сознательно НЕ реализовано (и почему)

- **Полноценное автоматическое слияние правок одной записи** (не
  только добавлений) - при конфликте правки одной и той же записи
  умное слияние не пытается угадать "чья версия правильнее". Для
  команды 5-7 человек с редкими правками это разумный компромисс -
  усложнение ради редкого случая не оправдано.
- **Расширенные точки испытаний** (14 вместо обычных 8/9) - флажок
  `modifications.is_extended_template` в схеме базы уже есть, но сама
  логика чтения по смещённой раскладке ячеек Excel не реализована -
  отложено до появления реальной необходимости.
- **Плановое резервное копирование по расписанию** - не нужно при
  нечастом использовании базы (несколько раз в день, а не постоянно) -
  резервные копии и так создаются достаточно часто в момент
  синхронизации.
- **Полная очистка базы данных** (удаление всех насосов) - обсуждалась
  и была сознательно отклонена как слишком рискованная операция в
  условиях многопользовательской синхронизации (может стереть историю
  работы всей команды одним нажатием на одном компьютере).

## 7. Версия программы

`version.py` - единственное место, которое нужно менять при выпуске
патча/обновления (`VERSION = "1.0"`). Отображается внизу меню
настроек.
