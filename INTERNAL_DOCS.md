# PumpTestApp - внутренняя документация (логика и алгоритмы)

Этот файл - НЕ для конечных пользователей программы. Он описывает, как
устроена логика внутри кода: как работают алгоритмы синхронизации,
защиты, резервного копирования и паролей. Предназначен для того, кто
будет дальше дорабатывать/поддерживать программу.

---

## 1. Архитектура многопользовательской работы

### 1.1. Общий принцип

Программа всегда читает и пишет только в свою локальную копию базы
данных (`database.get_active_db_path()` безусловно возвращает
`db_settings.get_local_db_path()`, даже когда включён сетевой режим).
Сетевой файл (`db_settings.get_network_db_path()`) - это общая точка
обмена, к которой программа обращается только в конкретные, явные
моменты:

1. При старте программы - сверка версий, копирование при необходимости
   (`db_sync.check_and_sync_at_startup`, вызывается из `main.py`)
2. Периодически во время работы (раз в 8 секунд, в фоновом потоке) -
   проверка изменений и присутствие пользователей
   (`gui.py: _RemoteCheckWorker`, `db_sync.check_for_remote_changes`)
3. По кнопке "Выгрузить" - копирование локальной базы в сеть
   (`db_sync.push_local_to_network`)
4. По кнопке "N -> L" - принудительное копирование сети в локальную базу
   (`db_sync.force_pull_network_to_local`)
5. По кнопке выбора "Полная замена сети" (при конфликте) - копирование
   локальной базы поверх сетевой безусловно
   (`db_sync.force_push_local_to_network`)

Прямая работа с сетевым файлом не используется - SQLite ненадёжен для
одновременной записи с нескольких машин по сети. Офлайн-режим работает
по тому же принципу: программа всегда работает с локальной копией,
пока пользователь сам не инициирует обмен с сетью.

### 1.2. Ревизия базы данных (db_meta.revision)

Каждая операция записи (`database.bump_revision()`) увеличивает
ревизию. Формат числа: `ГГММДД * 1000 + счётчик_за_день` (год идёт
первым) - это гарантирует, что обычное числовое сравнение "какая
ревизия больше" совпадает с хронологическим порядком независимо от
того, на стыке каких месяцев/годов происходит сравнение.

Отображение для человека - `database.format_revision_display()`,
разбирает число обратно и показывает в привычном ДДММГГ.счётчик виде.

### 1.3. Точка синхронизации (db_settings.last_sync_revision)

Отдельное значение - локальная ревизия на момент, когда локальная копия
последний раз точно совпадала с сетевой (после подтягивания сети или
после успешной выгрузки своих изменений). Сравнение
`database.get_current_revision()` с этим значением используется для
статуса "синхронизировано"/"есть изменения" (`db_sync.is_synced()`).

Если локальная ревизия больше сетевой на момент старта программы (есть
локальные изменения, ещё не отправленные в сеть) - точка синхронизации
не обновляется, статус корректно остаётся "есть изменения".

### 1.4. Лок-файл (db_lock.py)

Эксклюзивный лок-файл (`<сетевой_путь>.lock`) создаётся только на сам
момент записи в сетевой файл (копирование локального файла поверх
сетевого - доли секунды), не на всё время редактирования данных в
диалоге. Пока пользователь заполняет форму - к файлу базы никто не
обращается, лок не нужен.

Возраст лока для определения "протух ли он" (осиротел ли после
аварийного завершения программы) сравнивается по времени, записанному
ВНУТРИ содержимого самого лок-файла (`хост:пользователь:время`), а не
по метаданным файловой системы (mtime сетевой папки может ощутимо
отставать от локальных часов клиента). Порог - 60 секунд
(`LOCK_TIMEOUT_SECONDS`).

В локальном режиме (или когда сетевой режим не активен) весь модуль
`db_lock` не делает ничего - конкурентная запись в этом случае
невозможна в принципе.

### 1.5. Присутствие пользователей (db_sync.py)

Каждый компьютер раз в 8 секунд обновляет свой файл-метку
(`<сетевая_папка>/active_users/<имя_пользователя>.presence`) с текущим
временем внутри. Другие компьютеры читают эти файлы и считают, сколько
из них "свежие" (обновлялись в последние ~30 секунд).

Определение "свежести" не сравнивает время, записанное одним
компьютером, с текущим временем другого (часы разных машин в сети не
обязательно синхронизированы) - вместо этого используется
`_presence_seen_cache`: для каждого файла запоминается его последнее
замеченное СОДЕРЖИМОЕ и момент, когда это изменение было замечено, по
собственным часам читающего компьютера. Если содержимое файла
изменилось с прошлой проверки - пользователь активен прямо сейчас.

Список пользователей, когда-либо подключавшихся (`known_users.txt` в
той же папке `active_users`) - простой текстовый файл, обновляется
вместе с presence, но не хранится в самой синхронизируемой базе данных
(иначе статус "синхронизировано" менялся бы при каждом отклике
присутствия, а не при реальных изменениях данных).

Метка присутствия удаляется (`db_sync.remove_presence()`) при
подтверждённом закрытии программы и при переключении в локальный/полный
офлайн режим.

### 1.6. Защита от одновременного редактирования одной записи

У каждого насоса есть поле `last_edited_at` (точность до секунды,
обновляется при каждом `update_pump()`). При открытии записи на
редактирование это значение запоминается. При попытке сохранения
(`database.check_pump_unchanged()`) сверяется текущее значение в базе с
запомненным:
- совпадает - сохранение проходит без предупреждений
- не совпадает - кто-то другой успел сохранить изменения в эту же
  запись, пока пользователь её редактировал - показывается
  предупреждение с выбором (перезаписать/отменить)
- запись не найдена - значит, была удалена - сохранить невозможно

Подключено в основном диалоге редактирования насоса
(`gui.py: on_edit_requested`) и в редактировании истории/примечания
(`right_panel.py: manage_history`).

### 1.7. Уникальный идентификатор записи (uuid) и умное слияние

У каждого насоса есть поле `uuid`, используемое для сопоставления
записей между разными компьютерами при слиянии - не подходят ни
внутренний автоинкрементный `id` (может совпасть у записей,
независимо созданных на разных машинах), ни `pump_number` (в системе
допускаются законные дубли - один и тот же физический насос,
испытанный повторно).

Значение вычисляется детерминированно:
`uuid.uuid5(uuid.NAMESPACE_OID, f"pump-{id}-{created_at}")` - одинаковый
вход (id и время создания записи) всегда даёт одинаковый результат на
любом компьютере. При каждом запуске `database.init_db()` безусловно
пересчитывает uuid для всех записей и исправляет расхождения, если они
есть (дешёвая проверка - реальная запись происходит только при
несовпадении).

**Умное слияние** (`db_sync.smart_merge_push`) предлагается
пользователю, когда обычная выгрузка обнаруживает, что сеть изменилась
за время работы (`push_local_to_network` вернула `'network_ahead'`).
Алгоритм:
1. Читает минимальный снимок насосов из сетевой базы: `{uuid:
   (last_edited_at, pump_number)}`
2. Сравнивает с полными локальными данными
   (`database.get_all_pumps_full_for_merge()`)
3. Записи, чей uuid есть локально, но отсутствует в сети - безопасно
   переносятся (это новые добавления)
4. Записи, чей uuid есть в обеих базах, но с разным `last_edited_at` -
   считаются конфликтом правки, автоматически НЕ переносятся,
   сообщаются пользователю по номеру насоса отдельным списком
5. Подтягивает актуальную сеть (`force_pull_network_to_local`)
6. Заново добавляет найденные "новые" записи
   (`add_pump(..., pump_uuid=...)`, с сохранением исходного uuid - это
   делает повторный запуск слияния безопасным)
7. Выгружает результат обратно в сеть, под тем же локом

Правки уже существующих записей слиянием не переносятся - конфликт
такого рода всегда требует ручного разрешения пользователем.

### 1.8. Полная замена сетевой базы

`db_sync.force_push_local_to_network()` - альтернатива умному слиянию
для того же сценария (`network_ahead`). В отличие от слияния, это
**полная замена** файла сетевой базы локальной копией (обычное
копирование файла, не объединение данных). Любые записи, которые есть
в сети, но отсутствуют в локальной копии, после этой операции
перестают существовать в сети.

Применяется, когда пользователь сознательно хочет, чтобы сеть стала
точно такой же, как его текущая локальная копия - например, после
восстановления локальной базы из более старой резервной копии, когда
нужно откатить и сетевую версию тоже, а не слить с ней.

Перед перезаписью автоматически создаётся резервная копия ТЕКУЩЕЙ
сетевой базы (`_backup_network_copy()`, имя файла с префиксом
`pumps_network_`) - защита на случай, если что-то из заменяемых данных
впоследствии понадобится восстановить вручную.

### 1.9. Выбор действия при конфликте - единый диалог

При обнаружении `network_ahead` пользователю показывается диалог
`NetworkAheadChoiceDialog` (`dialogs.py`) с тремя вариантами сразу в
одном окне, каждый с кратким пояснением последствий:
- **Умное слияние** - обычный, безопасный выбор для случая, когда
  локально были только добавления
- **Полная замена сети** - целенаправленный выбор, когда сеть должна
  стать точной копией локальной базы (с явным предупреждением об
  удалении несовпадающих записей)
- **Отмена**

## 2. Пароли (auth.py)

Два независимых, равнозначных способа входа - подходит любой из них
(`auth.check_password()`):

1. **Основной пароль** - строковая константа `auth.DEFAULT_PASSWORD`
   прямо в коде. Меняется редактированием одной строки и пересборкой
   программы.
2. **Резервный (аварийный) пароль** - хранится локально на конкретном
   компьютере (не через синхронизацию сети), в скрытом файле
   `.pumpapp_sys/sys.dat` рядом с программой. Внутри файла - SHA-256
   хеш пароля, не сам пароль. Создаётся/меняется отдельным скриптом
   `generate_password_override.py` (не часть самой программы).

Если резервный файл существует - работают оба варианта одновременно
(резервный дополняет основной, не заменяет его на конкретном
компьютере).

Уровень защиты намеренно минимальный: без соли, без ограничения
количества попыток, без блокировки после неудачных попыток - задача
пароля - лёгкий барьер против случайных действий, а не защита от
целенаправленного доступа. Разделение ролей "только просмотр / полное
редактирование" достигается организационно (тем, кому нужен только
просмотр, просто не сообщается пароль), не средствами программы.

Действия, требующие пароля: удаление записи, добавление насоса
(вручную и через импорт Excel), работа с модификациями, редактирование
истории протокола.

## 3. Резервное копирование

### 3.1. Автоматическое (`db_sync._backup_local_copy`)

Создаётся перед каждой операцией, которая перезаписывает локальный файл
(подтягивание сети, старт программы при обнаружении более новой
сетевой версии). Пропускается, если копия с такой же ревизией уже
существует - ревизия однозначно определяет состояние базы, повторная
копия была бы идентична по содержимому.

### 3.2. По требованию пользователя (`db_sync.create_manual_backup`)

Создаётся принудительно, по нажатию кнопки "Сохранить копию" (левая
панель, рядом с "Выгрузить"; в компактном режиме списка - только
иконка, в расширенном - иконка с подписью "Сохранить текущую копию
БД"). В отличие от автоматической, создаётся всегда, даже если копия с
текущей ревизией уже есть - пользователь должен точно знать, что копия
сохранена именно сейчас, по его собственному действию. Имя файла
содержит маркер `_manual_`.

### 3.3. Копия сетевой базы (`db_sync._backup_network_copy`)

Создаётся перед полной заменой сетевой базы (см. 1.8). Ревизия в имени
файла читается из самого сетевого файла, а не из текущей активной базы
программы (та всегда локальная). Имя файла содержит префикс
`pumps_network_` - отдельный от обычных локальных копий.

### 3.4. Хранение и очистка

Локальные и сетевые резервные копии хранятся в двух независимых пулах
(`_cleanup_old_backups`), каждый со своим лимитом (`_BACKUP_KEEP_COUNT`,
30 штук) - сетевые копии создаются существенно реже, поэтому не должны
вытесняться частыми локальными.

После создания файла резервной копии его время изменения (mtime)
принудительно выставляется на текущий момент (`os.utime(path, None)`) -
без этого копия, скопированная с уже когда-то восстановленной (и потому
"старой" по времени файла) локальной базы, наследовала бы это старое
время и могла показываться в списке не как самая новая.

### 3.5. Список и восстановление (`db_sync.list_backups`,
`dialogs.RestoreBackupDialog`)

Каждый элемент списка - путь к файлу, дата создания, ревизия (если
известна - для копий старого формата имени не определяется), источник
(`local`/`network`), признак "создано вручную", количество насосов
внутри копии (`_count_pumps_in_backup` - краткое открытие файла в
режиме только для чтения ради одного агрегатного запроса).

Диалог восстановления показывает все эти данные в списке (с пометками
"· сетевая копия" / "· создано вручную" там, где применимо), позволяет
восстановить выбранную копию (`db_sync.restore_backup`) или удалить её
(`db_sync.delete_backup`) с подтверждением.

## 4. Журнал изменений (database.py: change_log)

Отдельная таблица в самой базе данных (в отличие от presence/
known_users - этот журнал синхронизируется вместе с остальными
данными, чтобы все пользователи видели одну и ту же историю).
Заполняется автоматически внутри `bump_revision()` при каждой операции
записи. Хранит последние 30 записей (`_CHANGE_LOG_KEEP_COUNT`), старые
автоматически вытесняются. Описание действия включает имя пользователя
(`getpass.getuser()`) в начале строки.

Просмотр - "Настройки → Журнал изменений базы данных".

## 5. Сортировка и постраничность списка насосов

### 5.1. Сортировка

Клик по заголовку столбца сортирует всю базу целиком (SQL-запрос с
`ORDER BY`), а не только уже загруженную страницу. Столбец
сопоставляется с полем базы данных через жёстко заданный список внутри
кода (`left_panel.py: _get_order_by_sql`) - не через пользовательский
ввод, что делает подстановку в SQL безопасной.

Индикатор сортировки (стрелка на заголовке) устанавливается после
перестроения таблицы, а не до - перестроение заголовков сбрасывает
индикатор, поэтому порядок операций важен.

Сортировка сбрасывается к значению по умолчанию (дата, по убыванию) при
переключении компактного/расширенного режима (разный набор и порядок
столбцов в этих режимах) и при нажатии "Сбросить фильтры".

### 5.2. Постраничность

Метка "Страница X из Y" и поле быстрого перехода на страницу имеют
фиксированную ширину - при росте номеров страниц текст меняет длину, и
без фиксированной ширины соседние элементы визуально сдвигались бы.
Метка "Показано записей" разделена на статичный текст и отдельную
метку только под число (тоже с фиксированной шириной) - по той же
причине.

### 5.3. Постраничность режима "Дубли"

Разбивка на страницы происходит по границам ГРУПП (все протоколы одного
насоса), а не по количеству строк - группа никогда не разрывается между
двумя страницами. Сначала группируются все совпадающие записи
(`_group_duplicates`), затем на страницу берётся заданное количество
групп целиком (`duplicates_groups_per_page`, 6 штук). Переключение
режима "Дубли" сбрасывает текущую страницу - номер страницы одного
режима не имеет смысла в другом (разный принцип разбивки).

### 5.4. Сортировка заказов

И в фильтре, и в сводной статистике заказы сортируются по убыванию
ЧИСЛОВОЙ части номера, без учёта буквенного префикса
(`database._order_number_sort_key`, извлекает цифры через
`re.sub(r'\D', '', str(order_number))`) - например, "К5666" идёт выше
"5487", несмотря на буквенный префикс. Обычная текстовая сортировка в
SQL расставляла бы их в порядке, не соответствующем реальной величине
числа - поэтому сортировка выполняется в Python после выборки из базы.

## 6. Графики

### 6.1. Разрешение и шрифт

Обе константы заданы в начале `right_panel.py`, рядом друг с другом, и
применяются единообразно и к обычному просмотру протокола, и к
сравнению дублей:

```python
_SCREEN_DPI = 130
_GRAPH_LEGEND_FONT_SIZE = 5
```

Значения подобраны опытным путём, менять без явного запроса не нужно.
При сохранении графика в файл разрешение временно повышается
независимо и значительно сильнее (`_FixedAspectToolbar.SAVE_DPI = 900`)
- для печати или увеличения даже экранной чёткости может быть
недостаточно, а для разового файла более высокая плотность не влияет на
отзывчивость интерфейса.

### 6.2. Сохранение в фиксированном соотношении сторон

Кнопка "Сохранить" на панели инструментов графика переопределена
(`_FixedAspectToolbar`) так, чтобы итоговое изображение всегда
сохранялось в соотношении 16:10, независимо от того, насколько широкой
или узкой отображается сама панель протокола на экране в момент
нажатия - размер фигуры временно меняется только на миг вызова диалога
сохранения и сразу возвращается обратно.

### 6.3. Ширина графика в режиме сравнения дублей

Виджет графика с политикой размера `QSizePolicy.Expanding` по
умолчанию сжимается под текущую ширину контейнера независимо от того,
что задано в `figsize` самой Figure - `figsize` влияет только на
исходное соотношение сторон при отрисовке. Чтобы график в режиме
сравнения дублей (пропорция 16:10) реально становился шире панели -
контейнеру задана явная минимальная ширина в пикселях (параметр
`min_width` у `_make_graph_widget`). Если панель окажется у́же этого
значения - появляется горизонтальная прокрутка.

## 7. Полосы прокрутки в фирменном стиле

`_GlowScrollBar` (left_panel.py) - подкласс `QScrollBar` с собственной
отрисовкой. Работает в обеих ориентациях (параметр `orientation`, вся
геометрия в `paintEvent` считается через `self.orientation()`). В
состоянии покоя - тонкая линия акцентного цвета, при наведении или
прокрутке колесом плавно расширяется симметрично в обе стороны от
центра, с настоящим свечением (ярче по центру бегунка, гаснет к его
краям).

Применяется двумя разными способами, в зависимости от того, что ещё
рисуется в том же родительском виджете:

- **Замена штатной полосы** (`table.setVerticalScrollBar(_GlowScrollBar(...))`)
  - используется для таблицы списка насосов. Полоса занимает своё
  обычное, зарезервированное место в layout (не поверх содержимого
  таблицы), Qt сам синхронизирует её значение и диапазон. Этот способ
  нужен именно здесь, поскольку у таблицы уже есть собственная система
  подсветки выделения/наведения строк, которая тоже претендует на
  верхний слой поверх содержимого - overlay-версия полосы конфликтовала
  бы с ней по z-порядку.
- **Overlay** (`_OverlayScrollArea` в right_panel.py) - используется
  для правой панели (и вертикальной, и горизонтальной прокрутки).
  `_GlowScrollBar` создаётся как независимый дочерний виджет `viewport()`,
  поверх содержимого, без резервирования места в layout (встроенные
  полосы Qt полностью отключены). Синхронизация значения/диапазона -
  вручную, через сигналы `rangeChanged`/`valueChanged` в обе стороны.
  Подходит здесь, поскольку больше ничего не претендует на z-порядок
  поверх viewport правой панели.

## 8. Тема оформления

Переключение между тёмной и светлой темой хранится через `QSettings` и
применяется ко всему приложению разом (`gui.py: apply_theme`) - вызовы
`refresh_theme()` у каждого крупного виджета (статус-бар, левая и
правая панели, все открытые диалоги) плюс `styles.retheme_widget_tree()`
для обхода всего дерева дочерних виджетов и замены цветов в их
стилях.

Виджеты, которые красят себя сами (например, светящиеся полосы
`_GlowLine`/`_GlowFrame`, управляемые собственным `refresh_all()`),
помечены свойством `_self_themed`, чтобы общий обход дерева виджетов
их пропускал и не конфликтовал с их собственной логикой перекраски.

Цвет текста в диалогах определяется через `styles.get_dialog_text_color()`
(графитовый на светлой теме, светлый на тёмной) - используется
единообразно во всех местах, где текст должен читаться на фоне,
который тоже меняется вместе с темой.

## 9. Импорт из Excel

Массовое добавление записей из Excel-файла (`excel_importer.py`)
защищено паролем - запрашивается перед открытием диалога выбора файла
(`gui.py: on_import_requested`), той же проверкой, что и остальные
защищённые действия.

Извлечение данных из листа (`extract_pump_data`) читает значения по
фиксированным позициям ячеек (например, номер насоса - строка 1,
столбец 6) - структура листа Excel должна соответствовать ожидаемому
шаблону. Номер заказа проходит через `utils.format_order_number()` (
убирает хвостовой float-артефакт из pandas, например "5644.0" → "5644")
и затем через `utils.normalize_order_number()` (приведение
кириллических омоглифов к латинице, верхний регистр).

При обнаружении в базе уже существующей записи с тем же номером насоса
и той же датой проверки - пользователю показывается предупреждение о
возможном дубликате с возможностью подтвердить добавление ещё раз или
пропустить лист.

## 10. Обратная связь

"Настройки → Обратная связь" открывает почтовый клиент, зарегистрированный
в системе по умолчанию, через стандартную ссылку `mailto:` - без какой-
либо серверной инфраструктуры отправки писем. Тема и тело письма
заполняются автоматически: версия программы, локальная ревизия базы, и
сетевая ревизия (с учётом того, активен ли сетевой режим и доступна ли
сеть в момент нажатия). Отправляется на основной адрес с скрытой копией
на второй - оба адреса заданы прямо в коде
(`dialogs.py: SettingsDialog.open_feedback_email`).

## 11. Что сознательно не реализовано

- **Автоматическое слияние правок одной и той же записи** (не только
  добавлений) - при конфликте правки умное слияние не пытается угадать
  "чья версия правильнее", такой конфликт всегда требует ручного
  разрешения. Решение рассчитано на команду в несколько человек с
  редкими одновременными правками одной и той же записи.
- **Расширенные точки испытаний** (14 вместо обычных 8/9) - флажок
  `modifications.is_extended_template` в схеме базы есть, но логика
  чтения по смещённой раскладке ячеек Excel не реализована.
- **Плановое резервное копирование по расписанию** - не требуется при
  нечастом использовании базы; резервные копии создаются достаточно
  часто в момент обычной синхронизации, плюс есть возможность создать
  копию вручную в любой момент.
- **Полная очистка базы данных** (удаление всех насосов) как функция
  программы - слишком рискованная операция в условиях
  многопользовательской синхронизации, способная стереть историю
  работы всей команды одним нажатием на одном компьютере.
